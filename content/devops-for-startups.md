## 什么是 DevOps？ ♾️

在回答这些重要问题之前，我应该先解释一下什么是 DevOps。它最初是作为开发与运维之间的桥梁而诞生的，旨在帮助这两个在目标和工作方式上大相径庭的领域能够协同工作。

![[devops-startup.png]]

多年来，DevOps 不断演变和成长，现已成为推动组织运转的成熟功能模型。如今，DevOps 几乎融入了所有现代工作框架和方法论中（市面上有如此多的 \*Ops！）。但最重要的是，我们已经学会了如何将 DevOps 构建为一个实用且可度量的工具。

### DevOps 与传统软件开发有何不同？

正如敏捷开发让软件交付摆脱了瀑布流模式，DevOps 也改变了运维的格局。

在 DevOps 出现之前，运维团队与开发团队是相互隔离的。此外，这两个领域有着完全不同的目标。在开发团队采用敏捷开发后，这些差异变得更加明显。运维的目标是稳定性，而开发则试图提高交付速度和单位时间内的交付数量。冲突在所难免。

除了其他变革之外，DevOps 的最初目标就是消除这种冲突，并将运维纳入开发环中。

### DevOps 框架 🗺️

今天，我们在 DevOps 领域主要使用两个核心框架：“三步法”（Three Ways）和 “CALMS”。这两个框架都不是什么新鲜概念，但遗憾的是，它们通常只在较成熟的组织中得到应用。事实上，使用其中任何一个框架都有助于推动 DevOps 的落地和理解。

#### 三步法（Three Ways） 1️⃣2️⃣3️⃣

“三步法”的概念在 IT Revolution 出版的《DevOps 实践指南》（The DevOps Handbook）和《凤凰项目》（The Phoenix Project）两本书中有着详细的阐述。任何想成为优秀 DevOps 践行者的人都应该读一读这两本书。

“三步法”包含以下三个原则：

- **第一步：系统思考（Systems thinking）** —— 该原则关注整个系统的性能，而不是特定的部门阻隔（Silos）。其目标是通过理解和改进价值流，来提高整体流程的有效性。

![[ways-startups-can-implement-devops.png]]

- **第二步：放大反馈回路（Amplify feedback loops）** —— 如果你熟悉“左移”（shift left）原则，就会觉得这个原则似曾相识。它强调了从右到左反馈回路的重要性。换句话说，后续阶段应该如何将情况及时反馈给前置阶段。

![[devops-for-startups-loop.png]]

- **第三步：持续实验与学习的文化（Culture of continuous experimentation and learning）** —— 敏捷开发和 DevOps 都非常推崇“实验”这一观点。对失败的恐惧是阻碍公司在现代市场中进行创新并取得成功的重要因素。

![[startups-using-devops.png]]

#### CALMS 框架 💡

第二个同样流行的框架是 CALMS。该框架包含五个支柱：

- **文化（Culture）**
- **自动化（Automation）**
- **精益（Lean）**
- **度量（Measurements）**
- **分享（Sharing）**

我们在这里不展开讨论每个类别。简而言之，它表明 DevOps 不仅仅关乎工具和自动化，也不仅仅关乎云和 [CI/CD](https://spacelift.io/blog/ci-cd-pipeline)，而是关乎组织的运行方式 —— 我们如何使用敏捷方法论（如精益）来提高生产力，我们如何共享知识，我们如何度量进度，以及我们如何自动化流程。此外，它还涉及到文化以及公司的运作方式。

显然，DevOps 不仅仅是关于工具或自动化。事实上，作为 CALMS 模型的一部分，自动化（在自动化原则下）仅占整个方法论的一小部分。

需要注意的是，你无法在组织中“一蹴而就”地实施整套 DevOps。这是一个漫长的过程，应该循序渐进地进行。这意味着任何规模的公司都可以选择适合其自身需求的环节来实施。

## DevOps 适合小公司吗？ 🏢

简短的答案是：当然适合！DevOps 不受员工人数、净增长或其他任何因素的限制。区别在于实施的内容和方式。但首先，组织必须回答一些根本性的问题：我们为什么需要 DevOps？我们想解决什么问题？我们想达到什么目标？

### 初创公司需要 DevOps 吗？

初创公司能从采用 DevOps 实践中获得巨大收益，因为这能让他们在确保基础设施具备可扩展性和可靠性的同时，实现更快的开发周期、更频繁的发布以及更高的敏捷性 —— 这对快速增长和创新至关重要。虽然早期的实施可能会比较轻量，但 DevOps 的核心原则在初始阶段就能提供长期的价值。

### 常见误区 ❌

初创公司最常犯的错误是招聘一名所谓的“[DevOps 工程师](https://spacelift.io/blog/who-is-devops-engineer)”，来充当系统管理员的角色，负责拿开发人员的代码并将其交付到生产环境，并且还要负责 On-Call。这个角色并不是真正的 DevOps 角色；他只是一个人 —— 在大多数情况下是一个系统管理员 —— 履行着该岗位的传统职责。

## DevOps 在初创公司中的角色 👤

DevOps 在初创公司中的角色应该主要集中在建立一条高效的交付链并对其进行度量。核心职责在于配置和管理云资源（因为大多数初创公司都会使用云服务），以及启用和强制使用[基础设施即代码（IaC）](https://spacelift.io/blog/infrastructure-as-code)和 CI/CD 系统。当然，还有监控，其中可观测性（Observability）发挥着非常重要的作用。

但这些都是技术层面的工作。每个初创公司和每个团队都需要一个基础来确保这些实践能够落地。因此，主要的精力应该放在向组织传递知识上。

为了跑得更快，仅仅引入 AWS、Kubernetes 和 Jenkins 是远远不够的。这解决不了问题，只会把问题转移到别处。我们需要构建起相应的**文化**。

在这一领域，DevOps 必须促进人与人之间的协作，让大家参与到分享中来（例如，通过开展内部交流会，介绍“我们的工作方式”以及“DevOps 如何提供帮助”），并展示在使用合适的工具和流程时所能带来的价值和收益。

在下表中，我们列出了 DevOps 流程和 DevOps 工程师可以提供帮助的事项，以及哪些不属于他们的职责范畴：

| 应该做的 (Do)                                                                               | 不该做的 (Don't)                                    |
| :------------------------------------------------------------------------------------------ | :-------------------------------------------------- |
| 帮助开发人员解决障碍                                                                        | 配置和管理开发人员的个人电脑                        |
| 提供与版本控制系统（VCS）进行适当集成的流程（如分支策略、Pull Request 策略等）              | 因为某些事情非常紧急而允许开发人员走“捷径”          |
| 培训开发人员如何使用 [DevOps 工具](https://spacelift.io/blog/devops-tools)（CI/CD、IaC 等） | 生活在自己的隔离孤岛中                              |
| 引导和影响开发人员从一开始就实施可观测性和安全性                                            | 在发生故障时，作为唯一的单点联系人承担 On-Call 职责 |

## DevOps 能为初创公司带来哪些好处？ 📈

让我们总结一下 DevOps 给初创公司带来的好处：

### 1. 促进协作

从本质上讲，[DevOps 专注于人与人之间的协作](https://spacelift.io/blog/devops-collaboration)。这不仅关乎日常工作，还关乎共享知识、提升他人技能以及为实验创造肥沃的土壤。

### 2. 提升交付效率

通过明确的流程使用合适的工具，可以提高交付率并缩短产品上市时间（Time-to-market）。

### 3. 建立标准

DevOps 优先考虑规范的标准和可重复性。模板、模块、自动化和文档对于提升开发标准至关重要。

### 4. 量化度量

DevOps 允许我们以可操作的方式度量工作。DORA 指标能让我们看清流程并实施针对性的改进。

### 5. 流程自动化

[DevOps 自动化](https://spacelift.io/blog/devops-automation)简化了开发和部署流程，使初创公司能够更快速、更高效地将产品推向市场。自动执行重复性任务可以最大限度地减少人为错误，并增强软件发布的连贯性和可靠性。

## 初创公司如何实施 DevOps？ 🛠️

如果初创公司想要践行 DevOps，就需要落地一些具体的实践。其中一部分已在上文列出，尤其是“第三步”。

如前所述，在初创公司中引入 DevOps 的目标是[实施恰当的流程](https://spacelift.io/blog/devops-implementation)。这意味着：

- **通过建立工作流来规范工作**。DevOps 定义了工作流，并帮助开发团队理解这些流程。
- **向团队提供关于流程的所有必要知识**。
- **建立反馈回路并使其具备可操作性**。这一点至关重要。不仅要建立反馈回路以获取状态感知，更要根据反馈采取行动。
- **建立交付流程**，包括工具、配置、模板、文档和知识共享。
- **成为知识共享工作的重要组成部分**。

所有这些都表明，组织并不一定需要一个名为“DevOps 工程师”的特定岗位，而是需要这样一套技能。当然，在大多数情况下，团队本身并不具备所有这些技能，因此必须招聘新的人才。

不过，我想强调一点。如果你在团队中引入了 DevOps 人员，千万不要只停留在技术层面。当然，对云、CI/CD 工具、IaC 和操作系统的了解非常重要，但你必须考察那些能够让 DevOps 推动组织变革的关键要素。

## 提示与最佳实践 💡

在实施 DevOps 实践之前，您应该考虑以下几点：

- **不要只关注工具** —— 虽然工具的妥善选择很重要，而且招聘的 DevOps 工程师必须熟悉它们，但在 DevOps 链条中，工具“仅仅”是流程的传送带。应该先建立起流程和工作方式，然后再选择支持该方法的工具。
- **不要成为开发人员的“专属快递员”** —— 是的，合理建立的 DevOps 实践的目标之一是创建和维护一条良好的交付链，但 DevOps 的存在是为了赋能开发，而不是代替开发人员做他们本该做的工作。协同效应和合理建立的流程将使开发人员更贴近生产环境和交付过程，从而赋予他们更多的控制权和所有权。
- **不要增加开发人员的认知负荷** —— 在 DevOps 中，我们必须以一种让开发人员能够管理交付（或部署）的方式来建立工具和流程，但同时要为他们配备一套工具集，使他们能够以尽可能不被打扰的方式来完成这项工作。这就是为什么我们在 Spacelift 提倡：让开发人员在不离开其现有工具环境的情况下交付基础设施。
- **专注于文化** —— 这一部分太容易被遗忘了。CALMS 框架将文化放在了第一位。“三步法”的核心也是建立恰当的工作文化。在这方面建立起正确的方法，能让技术团队更快速、更舒适地进行交付。
- **共享知识** —— 我们都知道“左移”原则，但它经常被错误地执行。在没有将相应的流程、规程和方法“左移”的情况下，仅仅把职责和任务强加给开发团队，会导致认知负荷急剧增加，甚至导致团队成员倦怠。
- 初创公司、小公司和其他组织往往表现出混乱的管理流程，并把大量的压力推给开发团队甚至个人。招聘一个经验非常丰富的人并交给他一大堆工作是很有诱惑力的做法。但问题是，人的精力是有限的，因此无论我们多么有经验，如果在超负荷运转，就难免会走捷径、犯错误。在人与人之间合理分担职责，并提供恰当的流程、工具和工作方式，才能让工作变得更轻松。
- **度量工作** —— DevOps 方法提供了多种度量方式。我们都使用监控和可观测性来监控产品的有效性，但流程的有效性呢？实施 DORA 指标来度量你在组织中实施的流程的有效性。
- **推行无指责文化** —— 我们常说敏捷开发和 DevOps 关乎实验。但是，如果不消除指责，你又如何能鼓励大家去进行实验呢？
- **实施“检查与调整”（Inspect & Adapt）思维** —— 拥抱敏捷和 DevOps 中的持续改进（Continuous Improvement）精神。不断优化你的流程并监控其效率。

## 关键要点总结 📝

- **DevOps 适用于各种规模的公司**。实施方式和主要侧重点可能有所不同，但在所有情况下，目标都是相同的：改进和提升开发与交付流程。
- **在实施 DevOps 实践时，不要仅关注工具集**。DevOps 是一种复杂的思维方式，它融合了工具、流程和度量。
- **Spacelift 可以为您提供合适的工具**，用于简化交付流程并提供支持性功能，从而优化每个人的开发弹性，帮助您组织基础设施的编排。
